Design Musketeer · Standard Operating Procedure

New POD Studio SOP

How the client-brief-to-print-file pipeline is built, run and changed. One generic system, switched per client by a locked Style Card. Covers product rules, frontend, Supabase backend, the n8n workflows, and every day-to-day procedure.

The one architecture rule

n8n owns sequence and visibility. Code (Supabase Edge Functions) owns decisions and contracts. Postgres owns state, concurrency and time. No client name ever appears in a workflow or a function; the pipeline only knows "load whatever this card's client says".

01Scope and locked decisions

The studio turns one client form submission into one approved, print-ready PNG, with a designer as the only gate. These decisions are fixed for v1; changing any of them is a new version of this SOP.

DecisionRuleConsequence
Client accessClients get one form link. No portal, no login, no review page.Every client-facing feature (share links, sign-off, credits) is v2 or out.
Outputs per cardOne generation per approval. No variations.Alternatives come from Regenerate, tracked as history on the same card.
Brief textThe text to print always comes from the client form, edited by the designer, never invented by the model.Exact-text rules in the prompt; QC checks the text appears once, verbatim.
Approval gateDesigner approval is the only trigger for generation. Nothing generates before it.Approval is a guarded state transition; a second click is a no-op.
Style memoryOne locked, versioned Style Card per client, injected into every prompt. The pipeline refuses to run without one.Onboarding a client is data entry, never a workflow change.
InfrastructureFresh Supabase project. Existing self-hosted n8n. Vercel for the board.DM Finisher's project and the DM POD project are never touched.
OrchestrationHybrid: n8n orchestrates, Edge Functions decide, Postgres owns state.No Code node over 20 lines; no 30-second sweeps. Keys live in exactly one place: the "Studio Config" node of WF-0.
Image engineKie.ai GPT Image 2.5 Sunburst, image-to-image. References are read by vision into the prompt AND attached to the model as inputs.Model, resolution and vision model are Settings fields; a client may override the model.

Client scopingThe header client selector scopes the board, Completed and New card to one client. Each client has its own form link.Briefs from a client link land only in that client's panel.

Never edit the live DM T-Shirt Engine workflow (DcdygzBz5GAoy2Zg). It is the reference implementation and is read-only. Never point anything at the DM POD Supabase project. Never commit a workflow export: the WF-0 config node carries the keys, so exports are never stored in the repo (only the SDK sources with placeholders).

02System overview

Six components, each with one owner. Data flows left to right; every hand-off is a row change in Postgres, never a direct call from the board to n8n.

Client form
Public · Vite route
  • Token link per client
  • 3 references, description, exact text
  • Anonymous insert via RLS
Studio board
Designers · Vite + React
  • Stage columns, live via Realtime
  • Card detail, edit and approve
  • Style Card editor, Completed panel
Supabase
State, concurrency, time
  • Postgres tables and RLS
  • Storage buckets, signed URLs
  • pg_net triggers, pg_cron sweeps
Edge Functions
Decisions · Deno, unit-tested
  • prompt-engine
  • qc-judge
  • Pure input to output, no vendor calls
n8n
Sequence and visibility
  • Generate, Edit, Finisher workflows
  • Vendor poll sub-workflow
  • Error and nightly workflows
Vendors
External APIs
  • Gemini vision (references, QC)
  • Kie.ai GPT Image 2.5 Sunburst, nano-banana-edit
  • ModelsLab upscale, Ideogram remove-bg

End-to-end path of one card

form submit→ card row · intake→ reference read (Gemini)→ designer edits and approves→ prompt-engine→ GPT Image 2.5 Sunburst→ qc-judge→ designer review→ edit-text / edit-region / regenerate→ finisher: upscale · remove-bg · 300 DPI→ delivered

The finisher is the DM Finisher chain already verified in production, ported unchanged except for its trigger and its table names.

Approval is the only transition a designer can make that spends money. The Approve button shows the fixed per-card cost and refuses if the client has no locked Style Card or if pipeline_paused is on.

5.2 Studio board /board

  • Columns are the stages from section 04, in order. waiting and failed sit at the far right.
  • Card tile shows client name, thumbnail of the current generation (or the first reference while in intake), print text first line, stage badge, and "in review for 3 h" computed from stage_entered_at. Turns amber after 4 minutes in any automated stage.
  • Header shows a queue indicator: "3 waiting · 2 running of cap 2", plus a Paused banner when the lead has paused the pipeline.
  • Client selector in the header scopes the board, Completed and New card to one client; "All clients" shows everything. Filters: by stage, mine (cards I approved).
  • New card (client from the selector or a dropdown; 1 to 3 references, brief, text, colour, placement) and New cards from images (one intake card per dropped image with shared brief fields) for designer-started work.
  • Realtime on cards and generations, with a 20-second poll fallback, the same pattern as DM Finisher.

5.3 Card detail /card/<id>

Left: brief and references

  • Every form field, editable until approval. Edits after approval apply only to the next regenerate.
  • Three references with the vision read under each: style, palette, subject structure, typography transcription.
  • Reference role override, only if the vision read got it wrong.
  • Print text as lines with an optional hierarchy tag: headline, sub, tagline.
  • Designer avoid-notes for this card, free text.
  • Style Card panel: the client's locked card version, with a link to the editor. Red if none is locked.

Right: generations and actions

  • Horizontal strip of every generation, newest first, with kind and QC verdict; a "make current" button on each.
  • Large preview of the current generation with a previous/current blink toggle.
  • QC report: nine points plus palette, Style Card violations and cropping, rendered as pass/fail lines with the model's note.
  • Structured magic prompt, editable per section before Regenerate.
  • Actions: Approve · Accept · Edit text · Edit region · Regenerate · Reject with reason · Park · Retry · Duplicate card.
  • Lead only: link to the n8n execution.

6.4 Triggers and schedules

  • cards insert → pg_net POST to /webhook/studio-intake (reference read).
  • cards stage becomes approved → pg_net POST to /webhook/studio-generate.
  • generations insert with kind ≠ generate → pg_net POST to /webhook/studio-edit.
  • fin_jobs status becomes queued → pg_net POST to /webhook/finisher-dispatch.
  • style_draft_requests insert → pg_net POST to /webhook/studio-style-draft.
  • pg_cron every 2 minutes → requeue_stale(), then one nudge to each dispatcher if anything is queued. pg_net is fire-and-forget with a 2-second timeout, so the sweep is the safety net, not an optimisation.
  • pg_cron nightly 02:00 → POST to /webhook/studio-lessons.

6.6 RLS summary

  • Designers and the lead: select all studio rows; update cards until approved; update review fields on generations; insert Style Card versions; no deletes except cards in failed or delivered.
  • Anon with a valid client token: insert one card and upload three references. Nothing else.
  • Worker (anon key plus secret header): select and update cards, generations, fin_jobs; insert generations, fin_job_events, design_lessons. Never delete.
  • All exemplar and lessons queries are filtered by client_id inside the function, and the policies enforce the same filter, so one client's history can never reach another client's prompt.

07Style Card and magic prompt

The Style Card is the per-client aesthetic contract. The magic prompt is assembled in layers, in a fixed order, from data the pipeline already has. Neither contains a client name; both are looked up by the card's client id.

  • Every generation stores the card id, version and a JSON snapshot, so any output can be audited.

7.2 Magic prompt assembly order

  1. Hard print rules from the active template: flat grey background, isolated artwork, no mockup, no borders, visible margin on all sides, known print defects to avoid.
  2. Style Card rendered as prose from the JSON above, including the forbid list as negatives.
  3. Client lessons: active rows from design_lessons for this client, then global ones.
  4. Exemplars: up to 5 approved prompts for this client as few-shot, once the client has 10 or more approved cards.
  5. Reference reading for this card: art style, palette, subject structure, typography transcription, with the reference role rule "style only, do not copy the subject" unless the tier says otherwise.
  6. Similarity tier (1 to 5) chosen by the designer or the client default, controlling how close to the references the subject may be.
  7. Brief: description, garment colour, placement, avoid-notes.
  8. Text slot: the print text lines, verbatim, with the exact-text rules: render once, spelled exactly, in the Style Card's typography, no extra words.

The engine outputs structured JSON with one key per layer plus a text slot, and a rendered paragraph in that order. The designer can edit any section before Regenerate; the render is redone from the edited JSON.

7.4 Lessons loop

Every rejection carries a reason from a fixed list: text_wrong, spelling, colour, style_drift, subject, background_artifact, placement, other. The nightly workflow groups the day's rejections by client and reason, asks the model to distil at most three new rules, and inserts them as inactive rows for the lead to activate. Style-drift rejections are keyed to the Style Card version so a bad version shows up quickly.

08n8n workflows

Nine small workflows on the existing self-hosted instance, in the "Print on demand" folder. Every workflow loads the shared WF-0 config on its first step, checks the secret header with an IF node, calls Supabase with the shared secret, and hands decisions to the Edge Functions. Sources are the SDK files under n8n/ in the repo; the canvas is generated from them.

8.1 Workflow rules

  • No Code node longer than 20 lines. The only exception is the 300 DPI stamp, which is kept exactly as it is.
  • Keys live in one place: WF-0 "Studio Config" (studio secret, Ideogram, imgbb, ModelsLab). Kie and Slack stay as n8n credentials bound by id. Never commit a workflow export.
  • Every vendor wait goes through the one Poll sub-workflow at a 6-second minimum interval, or through Wait-on-webhook when the vendor calls back. No workflow may hold its own poll loop.
  • Every workflow has the Error workflow set in its settings. Successful executions of the dispatcher and nightly workflows are not saved.
  • Each stage writes stage, stage_entered_at, last_error and n8n_execution_id in the same PATCH it already needs.
  • Changes are made in the editor or by importing JSON exported to git. The MCP update tools are not used on live workflows.

09Operating procedures

Numbered because order matters. Each step names who does it and what "done" looks like.

P1 · Onboard a new client

  1. Create the client row: name, garment colours, target print size, default similarity tier. LeadThe client appears in the board filter.
  2. Copy the form link from the client row and send it to the client. LeadOpening the link shows the form with the client's name.
  3. Wait for the first submission. WF-1 reads the references and drafts Style Card version 1. SystemThe card is in review and the Style Card panel shows "Draft".
  4. Open the Style Card editor, correct the draft against the references and your own read of the client, and lock it. DesignerVersion 1 shows as locked; the card's Style Card panel turns green.
  5. Continue with P2. Nothing generates before the lock. Designer
Why

The workflow, the prompt engine and the QC judge never change for a new client. Only rows change. That is the whole point of the Style Card.

P2 · Review and approve a card

  1. Open the card from the review column. Read the brief, the three references and the vision read. Designer
  2. Fix the print text lines and tag hierarchy if it matters. The text must be exactly what will print. DesignerNo spelling doubts remain; each line is one element.
  3. Set placement and similarity tier. Add avoid-notes for anything the references contain that must not be copied. Designer
  4. Confirm the Style Card panel is green. If red, do P1 step 4 first. Designer
  5. Click Approve. Confirm the cost in the dialog. DesignerCard moves to approved, then generating within a minute.
  6. If the card stays in approved for more than 5 minutes, check the Paused banner and the queue indicator, then see P8. Designer

P3 · Review a generation

  1. Open the card from needs_review. Read the QC report before looking at the image. Designer
  2. Check the print text against the brief with the blink toggle if there was a previous generation. Designer
  3. Check style against the Style Card panel: palette, linework, forbid list. Read any listed violations. Designer
  4. Decide: Accept (P5), Edit text or Edit region (P4), or Regenerate (P4). Rejections require a reason from the list. DesignerThe card leaves needs_review.

P4 · Edit text, edit region, regenerate

  1. Edit text: the dialog prefills the old text from the brief. Type the new text. Optionally add an instruction. Submit. DesignerA child generation appears in the strip; card is in editing.
  2. Edit region: drag a rectangle or lasso around the problem on the preview. Write what should change inside it. Submit. DesignerSame as above; after return, drift_pct is under 3% or the card is flagged.
  3. Regenerate: pick the rejection reason, edit any section of the magic prompt, submit. DesignerNew generation with kind regenerate and the edited prompt stored.
  4. Return to P3 when the card is back in needs_review. After three rounds on one card, ask the lead to look at the Style Card or lessons before continuing. Designer

P5 · Accept and deliver

  1. Click Accept on the generation you want. DesignerCard moves to finishing; a finisher job appears.
  2. Wait for delivered. Typical time is 2 to 4 minutes; the ModelsLab step is the slow one. System
  3. Open the Completed panel, check the metrics badge (pixels, 300 DPI, transparent background), download the PNG. DesignerFile opens with a transparent background at the target size.
  4. Send the file to the client by your usual channel. Delivery email automation is a v2 item. Designer

P6 · Change a client's Style Card

  1. Open the Style Card editor, click New version. It copies the current locked version into a draft. Designer
  2. Edit and lock. Write one line in the version note saying what changed and why. DesignerThe new version is current; older cards keep the version they were generated with.
  3. Regenerate one recent card and compare. If drift is worse, lock another version that reverts; never edit a locked one. Designer

P7 · Change a prompt template

  1. Insert the new template body as a new version with active = false. Lead
  2. Run the golden-brief test suite for prompt-engine against the new version. LeadAll fixtures pass: exact text present, Style Card tokens present, no forbidden tokens.
  3. Run the n8n Evaluations workflow on the 20 to 30 brief dataset. LeadQC pass rate is not lower than the current version.
  4. Activate the version in Settings. Note the date in the version row. Lead
  5. Watch the first 10 generations. Roll back by activating the previous version if rejection rate rises. Lead

P8 · Incidents

SymptomCheckAction

P9 · Change an n8n workflow

  1. Export the current version to git with the CLI backup before touching anything. Lead
  2. Make the change in the editor. Keep Code nodes under 20 lines; if logic is growing, it belongs in an Edge Function. Lead
  3. Run one test execution with a real card in a test client. Check the row was updated and the Error workflow did not fire. Lead
  4. Export again, grep the export for key-shaped strings, commit. LeadGit holds the new version; the export contains no secrets.
  5. Never touch the T-Shirt Engine workflow. Copy ideas from it; do not edit it. Lead

P10 · Weekly review (15 minutes)

  1. Count cards delivered, rejection rate, and regen rounds per card by client. Lead
  2. Read the inactive lessons from WF-7; activate the ones that are true, delete the rest. Lead
  3. Look at any client whose style_drift rejections rose; schedule P6 with the designer who knows them. Lead
  4. Check vendor spend against the per-card price label; adjust the label if it is off by more than 20%. Lead
